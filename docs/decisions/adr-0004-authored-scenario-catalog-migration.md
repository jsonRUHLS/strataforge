# ADR-004: Migrate authored scenarios into the catalog

> Status: Accepted  
> Date: 2026-08-18

## Context

StrataForge originally stores software-pattern scenarios in the authored content package. These scenarios support rich pattern pages, but they are not independently addressable catalog entities and cannot directly support database-backed scenario browsing, relationships, filtering, comparison, or future composition workflows.

The application now provides:

```text
/scenarios
/scenarios/[slug]
```

These routes read scenario records and relationships from PostgreSQL.

A migration approach is required to move authored scenarios into the catalog without deleting or destabilizing existing authored pattern content.

## Decision

StrataForge will migrate authored scenarios incrementally into PostgreSQL through a reviewed manifest and idempotent seed process.

The migration flow is:

```text
Authored pattern content
→ scenario inventory
→ reviewed migration manifest
→ PostgreSQL catalog seed
→ scenario index and detail routes
```

The inventory is generated by:

```text
scripts/inventory-scenarios.ts
```

and committed as:

```text
docs/migrations/scenario-inventory.json
```

The canonical migration mapping is maintained in:

```text
packages/database/src/migrations/authored-scenarios.ts
```

The database seed consumes this manifest and upserts:

```text
Scenario
→ ScenarioPattern
→ ScenarioTechnology
```

## Rules

- Every catalog scenario has a stable, reviewed, kebab-case slug.
- A scenario may link to one or more catalog patterns.
- A scenario may have one or more authored source references.
- Similar wording does not automatically mean two authored entries represent one shared scenario.
- Existing catalog slugs remain stable when already used by routes or links.
- Technology relationships are added only when the technology exists in the catalog and the relationship is explicit.
- Missing referenced patterns or technologies fail the seed.
- Authored scenario content remains in the content package until database coverage is complete and the catalog model can represent the required content.
- Seed operations use upserts and compound relationship keys so repeated seed runs do not create duplicate records or links.

## Consequences

### Positive

- Scenario routes use a consistent catalog source of truth.
- Scenarios can be independently browsed and linked by stable slug.
- Pattern, scenario, and technology relationships become queryable.
- Migration progress is reviewable through the inventory, manifest, and coverage documentation.
- Repeated local or CI seed runs converge on the same catalog state.

### Trade-offs

- Scenario data temporarily exists in both authored content and the catalog.
- The migration manifest requires deliberate editorial review rather than fully automatic conversion.
- New scenario entries must reference patterns and technologies that have already been seeded into the catalog.
- Pattern detail pages continue to rely on authored content until their broader migration is complete.

## Alternatives considered

### Read authored scenarios directly at runtime

Rejected because it preserves the current content-only model and does not create independently queryable catalog records or database relationships.

### Automatically generate permanent manifest entries

Rejected because automated extraction cannot reliably determine canonical names, stable slugs, duplicates, shared scenarios, or correct technology relationships.

### Migrate all scenarios in one change

Rejected because it creates a large, difficult-to-review change and increases the chance of incomplete or incorrect relationships.

### Replace authored content immediately

Rejected because existing pattern pages still rely on richer authored fields and deleting them would risk feature regressions.

## Validation

Each migration batch must:

```bash
pnpm inventory:scenarios
pnpm --filter @atlas-patterns/database build
pnpm --filter @atlas-patterns/database seed
pnpm --filter @atlas-patterns/database seed
pnpm lint
pnpm build
```

The second seed run must complete without duplicate scenario or relationship records.
